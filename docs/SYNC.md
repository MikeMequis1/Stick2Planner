# Connection and synchronization

## Overview

The app is local-first: schedule, notes, and Caixinha work without a server.
Synchronization is **optional** and happens between the local SQLite database and
a self-hosted server. Nothing is deleted from the device while the server is
offline.

Three credentials are different:

| Item | Where it lives | What it is for |
| --- | --- | --- |
| `ADMIN_TOKEN` | server `.env` | log in to the web pairing page |
| pairing token | QR/code generated by the page (TTL 5 min, single use) | authorize a device |
| device token | `flutter_secure_storage` on the device | authenticate sync and pull |

## Obtain the ADMIN_TOKEN

The server **does not create** the `ADMIN_TOKEN` on its own: it reads the
variable from the environment. The process is:

1. Generate a strong token in the stick2server repository:
   ```bash
   dart run bin/server token
   # alternative: openssl rand -hex 32
   ```
   The command prints a random value and does not change the running server.
2. Write the value to the server's `.env` file:
   ```dotenv
   ADMIN_TOKEN=generated-value
   ```
3. Recreate the service to load the new value:
   ```bash
   docker compose up -d --force-recreate
   ```
4. To check the value already configured:
   ```bash
   grep '^ADMIN_TOKEN=' .env
   ```
5. Use that value on the web page login screen.

The `ADMIN_TOKEN` is an administrative password; it is not the device token.
Changing it ends in-memory web sessions, but does not revoke devices that are
already paired. Keep `.env` out of Git and with restricted permissions.

## Prerequisites

1. Server running (`docker compose ps` → `healthy`).
2. Device reaching the server over LAN or Tailscale.
3. App installed and opened at least once (local database created).

Quick check in the browser: `<PUBLIC_URL>/v1/health`.

## Connection flow (first time)

### 1. Generate the QR on the server

1. Open the URL configured in `PUBLIC_URL` (LAN or Tailscale).
2. Enter the `ADMIN_TOKEN` generated in the previous step.
3. The page shows:
   - pairing QR (renewed while the page is open);
   - equivalent text code;
   - devices already paired.
4. Use the language button at the top to switch between **Portuguese/English**;
   the choice is saved in the browser and the page updates without reloading.

The QR contains `{url, serverId, pairingToken}`. It **expires in 5 minutes** and
can only be used once.

### 2. Pair on the app

On the device:

1. **Settings → Connection and synchronization**.
2. Tap **Pair this device**.
3. Scan the QR or paste the code.
4. Confirm.

Pairing does everything at once:

- saves the server URL;
- stores the device token in secure storage;
- enables automatic synchronization;
- triggers an immediate sync.

**There is no need to save the URL or test the connection before pairing.** The
code already carries the correct address.

### 3. Check

The section should show:

- **Paired · N pending**
- last sync;
- last report/error, if any.

## What each button does

The synchronization card in **Settings → Connection and synchronization** shows
only the state and the actions. The address and the test are on the **Connection
address and test** screen, opened by the button of the same name.

| Control | Where | Requires pairing? | Effect |
| --- | --- | --- | --- |
| **Connection address and test** | Settings | no | opens the dedicated screen |
| Address field | connection screen | no | only edits the text |
| **Save address** | connection screen | no | saves the URL; does not authenticate or pair |
| **Test connection** | connection screen | no | queries `/v1/health`; validates network/URL, does **not** pair |
| **Pair this device** | Settings | no | exchanges the code for a token and sets URL + token + automatic; becomes disabled after pairing and the card shows "Paired: <name>" |
| **Sync now** | Settings | **yes** | disabled until a token exists; performs push/pull |
| **Automatic synchronization** | Settings | **yes** | disabled until paired; turns on the triggers |
| **Disconnect from this server** | Settings | yes | deletes URL/token and turns off automatic; local data remains |

Recommended order:

1. (Optional) **Connection address and test** → type URL →
   **Save address** → **Test connection**;
2. **Pair this device** (QR/code);
3. **Sync now**, if you want to force it.

In short: **testing does not pair; pairing already configures; sync only works
after pairing.**

## Check before synchronizing

Before any sync (manual, automatic, or via the cloud), the app queries
`/v1/sync/stats` and counts the active local data:

- post-its;
- notes;
- events;
- tasks;
- history;
- tags.

If both sides have data and the post-its/notes/events/tasks/tags counts are
different, the operation is interrupted when this is the first sync or when
there are no pending local changes in the outbox. The screen shows the
comparison. Choose:

- **Keep local:** sends notes, post-its, tags and events from this device; the
  server starts reflecting this set and removes what does not exist here
  (history is preserved as an audit trail);
- **Keep remote:** replaces the local content with the server's set, including
  tags;
- **Cancel:** changes neither side.

When there are pending local changes, normal sync continues: the difference is
explained by data that will still be sent. If automatic sync finds the
divergence, it **overwrites nothing**: it stays in "Review required", the cloud
changes state, and the user decides in Settings → **Review now**.

## Cloud icon at the top

The icon next to Settings summarizes the state and opens **Settings** already
scrolled to the synchronization section:

| Icon | State |
| --- | --- |
| cloud with slash (gray) | device not paired |
| cloud with synchronization | sync in progress |
| cloud with slash (red) | last sync failed |
| cloud with up arrow | there are pending changes |
| cloud with check | paired and no pending items |

## When sync happens

- On app open/resume.
- After a local change (debounce of ~2 s).
- When reconnecting to the network.
- Every ~15 min via WorkManager (best-effort, with network).
- On the **Sync now** button.

Failures do not block the interface: the local queue remains and the error
appears in the status. If the check requires a choice, automatic sync is
suspended until the user decides.

## Event recurrence

- Post-it payloads carry `recurrence` and `recurrenceInterval`.
- The server stores them opaquely; occurrences are generated on the device for
  the visible period and are not separate records.
- Older payloads without the fields default to no recurrence and interval 1.
- Post-its also carry optional `timeMinutes` and `tagIds`; tag definitions use the
  `tag` sync entity. Older payloads default to no time and no tags.

## Tags

- Tags are a first-class sync entity (`tag`): id, name, tone, timestamps and
  tombstone travel in the payload.
- Post-its carry `tagIds`; a shared tag can be referenced by several events and
  tasks. Pull applies tags before notes/post-its so associations find the tag.
- Creating or editing a tag records its own outbox row. Deleting a tag sends a
  tombstone; receiving it removes the tag from local post-its without deleting
  them.
- Tags count in the local/remote review and in keep-local/keep-remote
  replacement, together with post-its and notes.

## Routines

- Routines and their per-day completion states are local-only in this version;
  they are not sent to the server. Therefore there is no server receipt date that
  could overwrite `createdAt`.
- `createdAt` is the routine record creation instant and is preserved on edits.
  Occurrences are only shown on or after its local calendar date, so an offline
  gap or a delayed sync can never generate activities before the routine
  existed.
- If routine sync is added later, the payload must carry `createdAt` and the
  merge must keep the older/original creation instant instead of the receipt
  time.
- Post-it reminders (`reminderMinutes`) travel inside the post-it payload and are
  stored opaquely by the server.

## Notes and links

- A **note is an atomic unit**: title, type, Markdown, lines/checklists, IDs,
  and state travel together.
- Linked post-its carry `noteId`; copied excerpts (`noteExcerpt`) remain as an
  independent snapshot.
- Deleting a note creates a tombstone; linked post-its are unlinked locally and
  synchronized as their own changes.
- Application order on pull: **tags → notes → post-its → history** (respects FKs
  and tag references).
- Conflict: the highest `updatedAt` wins. The losing version is preserved as
  `[Conflict] <title>`; for notes, the lines receive new IDs.
- Identical content does not create a copy; a server tombstone with local
  content creates a copy before deleting.

## Devices and revocation

- Each installation has its own `deviceId` and individual token.
- Rename/revoke: web page → device list.
- Revoked token → sync responds **401**; pair again to recover.
- The initial name comes from the Android model; it can be corrected on the
  page.

## Common problems

| Symptom | Probable cause | Action |
| --- | --- | --- |
| `Failed host lookup` | MagicDNS/private DNS on Android | use `http://<host-ip>:8090` or adjust private DNS/Tailscale |
| `Connection refused` | wrong port/URL or tunnel closed | **Test connection**, check `:8090` |
| **401** | token revoked/expired | pair again |
| Pending items do not decrease | server offline or network error | check the last error; try **Sync now** |
| QR expired | more than 5 min/single use | generate a new one on the page (renews itself) |
| Device shows as "Tablet" | old pairing | rename on the page or pair with the updated app |

## Security

- Tokens are not included in backups, logs, or the local database.
- The web page requires `ADMIN_TOKEN`; in-memory session with an HttpOnly
  cookie.
- Service restricted to LAN/Tailnet; do not publish the port to the internet.
- Revoking removes access immediately.
