# Synchronization with Stick2Server

Synchronization is optional. Stick2Planner is fully usable offline; when a
self-hosted Stick2Server is configured, local changes are pushed and remote
changes are pulled. The server is never the primary database.

Server repository: [github.com/MikeMequis1/stick2server](https://github.com/MikeMequis1/stick2server)
(deployment, Docker Compose, API and server tests live there).

## 1. Overview

```text
Stick2Planner device                         Stick2Server
┌──────────────────────┐                    ┌────────────────────────┐
│ SQLite (source)      │                    │ SQLite                 │
│ sync_outbox          │  POST /v1/sync     │ opaque entity payloads │
│ sync_bases           │ ─────────────────► │ per-item rev           │
│ sync_row_states      │ ◄───────────────── │ change log + cursor    │
│ secure token         │  acks/conflicts    │ device tokens          │
└──────────────────────┘                    └────────────────────────┘
```

- One request carries local changes and the pull cursor.
- Each entity is `postIt`, `note`, `history`, `tag`, `routine` or
  `routineExecution`.
- The server stores payloads opaquely and does not interpret tags, recurrence,
  routine cards or reminders.
- Local writes land in SQLite and in the outbox in the same transaction.
- The device can stay offline indefinitely; pending changes remain queued.

Current compatibility: Stick2Server **0.2.3** targets Stick2Planner **0.10.4**.
The server keeps accepting older clients.

| Server | App behavior |
| --- | --- |
| 0.2.2+ | Accepts the atomic `routine` entity |
| 0.2.3+ | Accepts `routineExecution` history |
| below 0.2.2 | Routine changes stay in the local outbox; other entities sync normally |
| below 0.2.3 | Routine executions stay in the local outbox; routines still sync on 0.2.2 |

The app checks `/v1/health` before deciding which entities it may send.

### Entity payloads

- `postIt` carries the complete record, including `timeMinutes`, `tagIds`,
  `recurrence`, `recurrenceInterval`, `recurrenceEndDate`,
  `occurrenceStatuses`, `seriesId` and `reminderMinutes`. Older payloads default
  to no time/tags/recurrence.
- `note` is atomic: title, type, Markdown, lines/checklist IDs and state travel
  together. `tag` definitions travel separately and are applied before post-its.
- `history` is append-only audit data. An orphan entry whose post-it no longer
  exists is skipped instead of failing the whole pull.
- `routine` is atomic: name, details, mode, weekdays, `createdAt`, `updatedAt`,
  tombstone, simple items/completions and nested `sections`/`intervals` for
  complete routines. Reminder configuration travels inside the same payload.
- `routineExecution` is immutable append-only history with a stable ID and
  `dedupeKey`, so repeated notification taps or pushes cannot duplicate it.

## 2. Credentials

Three different credentials exist:

| Credential | Stored where | Purpose |
| --- | --- | --- |
| `ADMIN_TOKEN` | server `.env` | Log in to the server web page and admin API |
| Pairing token | generated by the server page/CLI, TTL 5 min, single use | Authorize one device |
| Device token | `flutter_secure_storage` on the device | Authenticate `/v1/sync`, stats and snapshot |

Do not confuse them. The `ADMIN_TOKEN` is not the device token, and a device
token cannot administer the server.

### Generating the ADMIN_TOKEN

The server reads `ADMIN_TOKEN` from the environment; it does not create one at
startup. In the stick2server repository:

```bash
dart run bin/server token
# or: openssl rand -hex 32
```

Write the value to `.env`:

```dotenv
ADMIN_TOKEN=replace-with-a-generated-value
PUBLIC_URL=http://192.168.0.10:8090
```

Recreate the service so the new value is loaded:

```bash
docker compose up -d --force-recreate
```

Check the configured value on the host, if needed:

```bash
grep '^ADMIN_TOKEN=' .env
```

Keep `.env` out of Git and restrict its permissions. Changing `ADMIN_TOKEN`
invalidates in-memory web sessions but does not revoke already-paired devices.

## 3. Server prerequisites and quick check

1. Stick2Server is running (`docker compose ps` → healthy).
2. `PUBLIC_URL` is the address the device will use (LAN, VPN/Tailscale or HTTPS
   reverse proxy).
3. The device can reach that address.
4. The app has been opened at least once, creating its local database.

Browser check:

```text
<PUBLIC_URL>/v1/health
```

Expected response includes `ok`, `version` and `serverId`.

For full server installation, upgrades, volumes and backup, follow the
[stick2server README](https://github.com/MikeMequis1/stick2server#readme). This
document only covers the app side of the integration.

Server endpoints used by the app:

| Method | Route | Auth | Purpose |
| --- | --- | --- | --- |
| `GET` | `/v1/health` | None | Health, version and `serverId` |
| `POST` | `/v1/pair` | Pairing token | Exchange a pairing token for a device token |
| `POST` | `/v1/sync` | Device token | Push and pull in one request |
| `GET` | `/v1/sync/stats` | Device token | Active data counts |
| `GET` | `/v1/sync/snapshot` | Device token | Full remote snapshot (keep remote) |
| `POST` | `/v1/sync/replace` | Device token | Replace the remote set (keep local) |

Administrative routes (`/v1/admin/*` and the web page APIs) use the
`ADMIN_TOKEN`, not a device token.

## 4. Pairing

### On the server

1. Open `PUBLIC_URL` in a browser.
2. Sign in with `ADMIN_TOKEN`.
3. The page shows a pairing QR code, an equivalent text code and the paired
   device list.
4. The QR renews while the page is open (5-minute TTL, single use).
5. The page switches Portuguese/English without reloading; the choice is stored
   in `localStorage`.

The QR/code contains a JSON payload with the server URL, `serverId` and
`pairingToken`. The app also accepts a compact `url|token` form for manual entry.

### On the device

1. Open **Settings → Connection and synchronization**.
2. Tap **Pair this device**.
3. Scan the QR code (Android) or paste the code (all platforms).
4. Confirm.

Pairing does all of the following atomically:

- saves the server URL;
- exchanges the pairing token for a device token;
- stores the token in secure storage;
- enables automatic synchronization;
- starts an immediate sync.

There is no need to save the URL or test the connection before pairing: the code
already carries the correct address.

## 5. Settings controls

The synchronization card shows state, pending count, last sync and last error.
The address and connection test live on a separate screen.

| Control | Requires pairing? | Effect |
| --- | --- | --- |
| **Connection address and test** | No | Opens the address/test screen |
| Address field | No | Edits the text only |
| **Save address** | No | Saves the URL; does not authenticate or pair |
| **Test connection** | No | Queries `/v1/health`; validates network/URL, does not pair |
| **Pair this device** | No | Exchanges the code for a device token and enables sync |
| **Sync now** | Yes | Runs the full push/pull cycle |
| **Automatic synchronization** | Yes | Enables change/resume/reconnect/background triggers |
| **Disconnect from this server** | Yes | Deletes URL and token, disables automation; local data stays |
| **Review now** | Yes | Opens the pending local/remote comparison |

Recommended order:

1. (Optional) save the address and test the connection.
2. Pair with the QR/code.
3. Use **Sync now** if an immediate sync is desired.

Testing does not pair; pairing already configures; sync only works after
pairing.

The cloud icon next to Settings summarizes the state and opens the
synchronization section:

| Icon | State |
| --- | --- |
| Cloud with slash, gray | Device not paired |
| Cloud with sync arrows | Sync in progress |
| Cloud with slash, red | Last sync failed |
| Cloud with up arrow | Pending changes |
| Cloud with check | Paired, no pending items |

## 6. Sync triggers

When paired and automatic sync is enabled:

- after a local change, with a ~2-second debounce (outbox watch);
- when the app resumes;
- when connectivity returns;
- on **Sync now**;
- every ~15 minutes on Android via WorkManager, network-restricted and
  best-effort.

Desktop has no periodic background worker; it syncs on the same triggers while
the app is open, plus the manual button. Failures never block the UI: the outbox
remains and the error appears in Settings.

## 7. Preflight review

Before a merge sync, the app queries `/v1/sync/stats` and compares active local
and remote counts:

- post-its;
- notes;
- events;
- tasks;
- tags;
- routines;
- history (shown for context; history is an audit trail and does not decide).

If both sides have data and the user-data counts differ, the operation stops
when this is the first sync or when there are no pending local changes:

| Choice | Effect |
| --- | --- |
| **Keep local** | Uploads the local snapshot and tombstones remote items that do not exist locally; history is preserved |
| **Keep remote** | Replaces local post-its, notes, tags and routines with the server snapshot |
| **Cancel** | Changes neither side |

If automatic sync finds this divergence, it does not decide: it stays in
**Review required** until the user chooses. Pending local changes explain a
count difference and allow the normal merge to continue.

## 8. Conflict handling

### Generic entities

Post-its, notes, tags and their associations use the same optimistic rule:

1. Push includes `baseRev`.
2. If `baseRev` is current, the server accepts and returns a new `rev`.
3. If not, the server returns its current version as a conflict.
4. The app compares `updatedAt`; the highest timestamp wins. A tie, or identical
   content, keeps the server version.
5. The losing local version is preserved as a `[Conflict] <title>` copy (new
   UUID; note lines get new IDs).
6. If local wins, `baseRev` is aligned and the change is retried once.

Deletion follows tombstones:

- a server tombstone with local content creates a copy before applying deletion;
- a local tombstone does not create a copy;
- ack removes the outbox row only if its `changeId` is unchanged. If the user
  edited during the push, the newer payload remains queued with an aligned
  `baseRev`.

### Routines

Routines are one atomic entity and use a three-way merge:

- `sync_bases` stores the last payload accepted by the server;
- on a revision conflict, the client merges `base`, `local` and `server` by
  stable IDs: scalars by field, items/cards/intervals by ID, completion dates as
  a set;
- independent edits to different elements are combined and re-sent;
- the same scalar or element changed differently keeps the server version and
  creates a local `[Conflict]` routine copy;
- conflict copies regenerate routine, card and interval IDs so they cannot
  overwrite the original structure.

Older clients that do not understand `mode`/`sections` cannot display complete
cards. Stick2Server protects stored complete cards when such a client updates a
routine without those keys; the old client still needs an update to edit cards.

### Application order

Remote changes are applied in dependency order. Tags go first, then notes, then
post-its; history, routines and executions follow in the order returned by the
server:

```text
tags → notes → post-its → history / routines / routine executions
```

Apply, acks, row revisions and the cursor are written in one local transaction.
A failure rolls back the pulled set; a network failure keeps outbox and cursor
intact.

## 9. Offline behavior

- No server, account or network is required for local use.
- Every mutation writes locally first; the outbox is the durable queue.
- Sync never deletes local data because the server is unavailable.
- A revoked token returns **401**; local data remains and the device must pair
  again.
- Routine/execution changes against too-old servers stay queued instead of
  failing the whole sync.
- Backup import clears sync queues and merge bases because they no longer
  describe the imported data. Device ID and server configuration are preserved.

## 10. Devices and revocation

- Each installation has its own `deviceId` and device token.
- The initial device name comes from the platform model; it can be corrected or
  renamed from the server page without re-pairing.
- Revoking a token from the page makes the next sync return **401**; pair again
  to recover. Local data is not deleted.
- The server page lists last access and supports rename/revoke.
- Signing out of the web page ends the administrative session only; it does not
  revoke paired devices.

## 11. Security

- Device tokens are stored with `flutter_secure_storage` (Android secure
  storage, Windows Credential Manager, Linux Secret Service).
- Tokens are not exported in JSON backups, not written to logs and not stored in
  the SQLite database.
- The server stores device tokens as SHA-256 and compares them in constant time.
- Pairing tokens are single-use and expire.
- The web page uses an in-memory session with an `HttpOnly`, `SameSite=Strict`
  cookie.
- Intended exposure is LAN, Tailscale/VPN or an HTTPS reverse proxy. Do not
  publish the server port directly to the internet.
- The app accepts cleartext HTTP for a self-hosted server on a trusted LAN/VPN;
  use HTTPS when exposing it through a proxy.

## 12. Diagnostics

| Symptom | Probable cause | Action |
| --- | --- | --- |
| `Failed host lookup` | Private DNS or MagicDNS resolution failure | Use `http://<host-ip>:8090` or fix private DNS/Tailscale |
| `Connection refused` | Wrong port/URL or tunnel closed | **Test connection**, check port 8090 |
| **401** | Token revoked/expired | Pair the device again |
| Pending items do not decrease | Server offline or network error | Check last error, then **Sync now** |
| QR expired | More than 5 minutes or already used | Generate a new code on the page |
| Device shows an old name | Paired before the label update | Rename on the web page or pair again |
| Review required keeps returning | Local/remote counts diverge | Choose **Keep local**, **Keep remote** or **Cancel** explicitly |
| Routine changes stay pending | Server older than 0.2.2 | Update Stick2Server |
| Execution history stays pending | Server older than 0.2.3 | Update Stick2Server |
| Pairing fails on Linux | No Secret Service/keyring | Start GNOME Keyring/KWallet |
| Sync works on USB tunnel but not Wi-Fi | Address points to `127.0.0.1` | Pair again with the LAN/Tailscale URL |

Useful checks:

```bash
curl -fsS http://<host>:8090/v1/health
docker compose ps
docker compose logs --tail=100 api
```

Server-side deployment and logs are documented in the
[stick2server repository](https://github.com/MikeMequis1/stick2server).
